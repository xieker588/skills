## 一、阻断级（Blocker）

### B1. 「基座选 AIRI」与「遵守 harness/loop engineering」及「用户最在意记忆+操控」三处自相矛盾
- **现象**：
  - `SKILL.md:3` 描述写"基于 Project AIRI"；`方案总成.md:104` 选型表 base=Project AIRI。
  - 但 `SKILL.md:21` 自己承认"AIRI 的记忆+电脑操控相对弱"，而这两点恰是用户第一诉求（`方案总成.md:8` 必备能力、`:5` 用户最在意）。
  - harness/loop engineering 的本意是**我们拥有编排引擎**；套一个完整 App（AIRI）当底座，等于把编排权交给别人，纪律名存实亡。
- **判定**：方向性矛盾，必须解决。
- **处置（已并入方案总成）**：用户「自建」指令明确——**改为自研 harness + loop 引擎**；AIRI / Open-LLM-VTuber 降级为「形象与语音/操控的参考模块（borrow，不 base）」。详见 `方案总成.md` 新增 §0.5「基座决策：自建优先」与修订后的 §4 选型映射。

## 二、主要缺口（Major）

### M1. 缺「自检子系统」——用户字面要求的工程能力未落地
- 现状：`方案总成.md:62-63` 仅有"可观测性（日志/打点）"，无主动自检闭环。
- 缺口：无周期性健康自检、记忆完整性校验、配置漂移检测、近期动作审计回放、自我校正触发。
- 处置：新增 §2.7「自检子系统（Self-Check Loop）」，定义 5 类自检 + 触发时机 + 校正动作（见方案总成）。

### M2. 语音-only 场景的 L2/L3 审批流缺失
- 现状：`方案总成.md:51-57` 定义了动作分级与"显式确认"，但整条链路是语音对话，用户手可能在忙/不碰键盘。
- 缺口：纯语音如何确认 L2 执行、L3 外部通信？无 UI/交互定义 → 安全围栏在语音场景下悬空。
- 处置：§2.4 补「语音确认协议」（复述+二次唤醒词确认 / 默认拒绝 / 危险动作零信任）。

### M3. 恢复语义不清——「不重复执行」未定义幂等
- 现状：`方案总成.md:48` 写"崩溃重启后…不丢记忆、不重复执行"。
- 缺口：已派发的 L2 命令（如"重命名文件""运行脚本"）进程被杀后是否幂等未说明；重放可能二次执行。
- 处置：§2.3 补「检查点与幂等」——动作带 id + 状态机（queued→dispatched→acked→done），dispatched 未 ack 的重启后进入人工裁决而非自动重放。

### M4. 延迟预算只有单点、无端到端
- 现状：`方案总成.md:95` 仅"STT→首字 < 400ms"。
- 缺口：缺 TTFT（LLM 首 token）、TTS 首字节、端到端 p95 预算，也无失败降级时的预算放宽说明。
- 处置：§3.2 补量化延迟预算表（本地/降级两套）。

### M5. 本地优先的硬件资源约束未建模
- 现状：`方案总成.md:9` 喊"核心链路本地优先"，`:108-111` 选型本地 LLM+Live2D+TTS+STT 同机。
- 缺口：无 VRAM/RAM/CPU 争用分析；同时跑 Ollama(qwen)+Live2D 渲染+STT+TTS 在消费级显卡上会抢显存，可能崩。
- 处置：§1 补「本地资源预算」小节（最低/推荐配置、进程优先级、显存分配上限、必要时的 LLM 回落 API）。

### M6. 记忆一致性——无去重/冲突/真值来源
- 现状：`方案总成.md:113-119` 三类记忆，写"摘要落盘 + 检索注入"，未说多 session 矛盾怎么办。
- 缺口：两个 session 上报冲突的项目状态、记忆条目重复/过期、volatile 状态与持久记忆谁为准，均无策略。
- 处置：§5 补「记忆一致性」——条目带时间戳+来源+置信；冲突时以最新带证据者为先，可疑项挂"待确认"不自动采纳。
